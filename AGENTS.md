# Repository Guidelines

## Проект и контекст

Проект «Плагин KickDuck1», рабочая директория — `KickDuck1`.
Общаться с пользователем на русском языке. Перед работой читать `README.md`,
`docs/CONTEXT.md` и актуальный `docs/PLAN.md`. Общие инструкции находятся
в `../AGENTS.md`; этот файл уточняет правила для KickDuck1.

## Структура

`Source/PluginProcessor.*` — DSP, APVTS и состояние; `Source/PluginEditor.*` —
GUI; `DuckingCurve.h` — общая геометрия кривой; `WaveformHistory.h` — история
аудио. `Tests/ProcessorTests.cpp` — регрессионные проверки. `docs/` — решения
и план. `build-dev/` — актуальная сборка; старый `build/` содержит устаревший
CMake-кэш, но также локальный исходный JUCE.

## Сборка и проверки

C++17, JUCE 8.0.10, CMake 3.22+, Linux; VST3 и Standalone.
Команды выполнять из корня проекта:

```sh
cmake --preset offline
cmake --build --preset tests
ctest --preset dev
cmake --build --preset plugin
git diff --check
```

Preset `offline` требует
`build/_deps/juce-src`; в новом checkout использовать `cmake --preset dev`
для загрузки JUCE. Ограничивать параллельную сборку тремя заданиями.
Сначала проверить изменённый DSP/GUI, затем собрать плагин для установки.
Указывать результаты проверок и границы автоматической валидации.

## Разрешения и рабочий процесс

Пользователь разрешил автоматически заменять VST3 в
`~/.vst3/KickDuck1.vst3` после успешной пересборки. Повторного
подтверждения для этой операции не требуется. REAPER запускает пользователь;
прослушивание и приёмку в DAW выполняет он. В конце итерации сообщать,
установлена ли новая сборка и что проверить в DAW.

## Стиль и архитектура

Сохранять существующий стиль C++: четыре пробела, скобки на отдельных строках,
camelCase для методов/переменных, PascalCase для классов. Не форматировать
несвязанные файлы. GUI и DSP должны использовать одну геометрию кривой.
В `processBlock` исключать аллокации, mutex, файловые операции и ожидания.
GUI получает безопасные snapshots; не читать playhead из GUI-потока.
Сохранять ID параметров, коды VST3 и совместимость состояния; менять смысл
параметров только с документированной миграцией и проверками.

## Git и завершение итерации

Перед правками проверять `git status --short`; сохранять существующие изменения.
Не добавлять в коммит build-артефакты, личные данные и HTML-экспорты переписки
без отдельного указания. История не имеет устойчивого формата сообщений;
использовать короткие описательные заголовки. Обновлять `docs/PLAN.md` и
`docs/CONTEXT.md` при существенных решениях и завершённых этапах.
