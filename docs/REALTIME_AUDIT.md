# Аудит DSP и обмена данными — 2026-10-13

Проверены прикладные пути processBlock, публикация кривой, обе waveform-истории,
измерители и GUI snapshot. Это аудит текущей Linux/x86-64 сборки, а не
доказательство отсутствия всех возможных гонок в плагине или хосте.

## Владение и синхронизация

- DSP работает с фиксированными массивами. Публикация кривой: три слота,
  сериализованные control/state writers, CAS-резервирование audio reader,
  release при освобождении; максимум две попытки чтения за блок, затем
  последний audio-owned cache. Содержимое слота не читается без владения.
- TriggeredWaveform: один producer владеет незавершённым кадром; GUI
  резервирует законченный слот. При занятом слоте чтение пропускается.
  Новая запись не может изменять зарезервированный кадр; версии монотонны.
- WaveformHistory: поля атомарные, но прежних acquire/release проверок
  поколения недостаточно для гарантии согласованного payload. Добавлены
  release fence после invalidation и acquire fence перед повторной проверкой.
  Если reader увидел новое поле, fence-синхронизация не позволяет принять
  прежний sequence. Данные перезаписанного слота отвергаются.
- Сброс истории теперь меняет resetEpoch до и после очистки. Snapshot,
  пересёкший reset, возвращает нули: повторное использование номеров
  поколений после clear не выдаёт новый звук за прежнюю историю.
- Модель DuckingCurve защищена mutex вне DSP; GUI использует try-lock.
  GUI не читает playhead. APVTS raw-lookup в установленном JUCE использует
  неизменяемую таблицу адаптеров без mutex; DSP читает атомарные значения.
- static_assert проверяет lock-free float, double, int, bool и счётчики
  истории на целевой сборке. Атомарность отдельных показаний не делает
  всю совокупность параметров одной транзакцией.

Предполагается обычный жизненный цикл хоста: processBlock и prepareToPlay
одного экземпляра не исполняются одновременно. push/clear имеют одного
producer; запрет одновременных writers относится и к историям. GUI может
читать во время lifecycle reset. Полное сохранение состояния включает
APVTS и кривую; оно не гарантирует единый sample-точный снимок всей
автоматизации, происходящей одновременно с сохранением.

## Измерение выделений памяти

Tests/AllocationProbe.cpp существует только в тестовой Linux-сборке.
Переопределён C++ new (включая aligned), линкер перехватывает прямые
malloc/calloc/realloc/posix_memalign/aligned_alloc вызовы из исполняемого
файла и статически связанного JUCE. Счётчик thread-local, сам не выделяет
память; самопроверка обнаруживает контрольные C++ и C выделения.

Измеряется только интервал processBlock: подготовка буферов, изменение
параметров и публикация кривой происходят вне интервала. Матрица: 44.1,
48, 192 kHz; блоки 1/17/64/512; mono/stereo; AUX on/off; AUTO/Audio/Host,
автоматизация Amount, Division и Bypass, публикация новой формы.
4608 callbacks: ноль C++ и перехваченных C heap allocations, включая
первый callback после prepare. Аудиопуть не содержит mutex, файловых
операций или ожиданий. Чужой playhead может выполнять собственную работу;
выделения внутри динамических библиотек хоста и полный системный malloc
этот перехват не покрывает. Это не профиль задержек callback.

GUI измерен отдельно: полный software paint после прогрева и dispatch
GUI-таймера. Эти числа включают JUCE, а не только наш код. Рендер не является
allocation-free: JUCE рисует линии/текст/кнопки с выделениями памяти.
В измеренном кадре: paint — 7142 C++ и 31400 перехваченных C heap вызовов;
timer dispatch — 27 C++ и 0 C heap вызовов. Числа зависят от выбранного
software renderer и GUI-состояния; это не норматив нагрузки.
Прикладные vectors для curve snapshots зарезервированы; Path верхнего
scope заранее получает ёмкость на 1600 точек и переиспользует её.
Прикладной updateMeters создаёт некоторые временные String, что относится
к GUI-потоку и не нарушает ограничения DSP. Оптимизацию рендера следует
делать по измерению нагрузки/частоты кадров, не переносить в DSP.

## Конкурентные проверки и пределы

```sh
cmake --preset offline
cmake --build --preset tests
ctest --preset dev -V
g++ -std=c++17 -O1 -g -fsanitize=thread -pthread -ISource Tests/RealtimeTests.cpp -o /tmp/kickduck-realtime-tsan
/tmp/kickduck-realtime-tsan
```

RealtimeTests проверяет согласованность связанных значений input/output/kick/GR
при 300000 публикациях с overwrite/reset, резервирование triggered frames
и чтение/запись GUI-модели кривой. Обычный и ThreadSanitizer прогон прошли
без обнаруженных ошибок. GCC предупреждает, что TSan не моделирует
atomic_thread_fence; корректность порядка кольцевой истории проверена
отдельно анализом протокола, не выводится из молчания TSan.

Весь JUCE/процессор и реальный хост под TSan не запускались. Существующий
stress test публикации runtime-кривой и headless DSP проходит обычным
прогоном; его пределы остаются такими же. GUI проверяется на пяти размерах
и screenshot; это не оценка живой плавности. Слуховая проверка, несколько
экземпляров, сохранение проекта и offline render в DAW остаются ручными.


## Дополнение — A/B и Undo/Redo, 2026-10-17

История работает только на control/message thread. Callback жеста сначала
проверяет атомарно сохранённый GUI thread ID и сразу возвращается на другом
потоке: MessageManager::isThisTheMessageThread здесь не вызывается, поскольку
JUCE защищает его mutex. GUI thread регистрируется при создании редактора
или в конструкторе процессора, если он уже на message thread.
Отдельный тест не-GUI жеста не обнаруживает аллокаций; stress-проверка
A/B/Undo во время DSP также проверяет конечные уровни и heap allocations.
Это не дополнительный полный прогон JUCE/процессора под ThreadSanitizer.
